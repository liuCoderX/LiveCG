# LiveCG 架构设计：实时字幕图文系统

> 目标：一套服务于**电竞（CS2 等）**与**传统体育（足球、篮球等）**直转播的在线包装系统——
> 数据自动驱动 + 导播/图文操作员手动控制，输出可直接叠加到 PGM 的透明图文信号。

---

## 1. 需求拆解

| 维度 | 电竞（以 CS2 为例） | 传统体育 | 系统共性要求 |
|---|---|---|---|
| 数据来源 | 游戏官方 GSI（CS2 Game State Integration）、HLTV/赛事方 API、Demo 解析 | 官方数据商（Opta、Sportradar、Stats Perform）、场馆计分器/计时器（串口、Daktronics、Swiss Timing 等）、人工录入 | 多源接入，统一模型 |
| 刷新频率 | 高（GSI 约 10 次/秒；血量、经济、击杀信息实时变化） | 中低（比分、时钟、换人、技术统计） | 毫秒级时钟需本地插值，避免靠推送刷新 |
| 典型图文 | 比分条、选手血量/经济条、击杀信息、回合结算、地图 BP、MVP、选手数据卡 | 比分时钟、人名条、换人、红黄牌、技术统计、阵容、积分榜 | 模板化、可复用、可换皮 |
| 操作方式 | 大量自动触发（回合结束弹结算） + 手动 | 以手动为主，比分时钟半自动 | 「预览 → TAKE → 下屏」的播出流程 |
| 可靠性 | 直播事故不可回退 | 同左 | 断线自动重连、状态可恢复、主备切换 |

另外，「字幕」在国内广电语境中既可以指**图文包装（字幕机）**，也可以指**语音转写字幕（ASR 实时字幕）**。本架构以前者为主体，并为后者预留了数据接入层的插槽（见 §6）。

## 2. 总体架构

```
 ┌──────────────── 数据接入层 Adapters ────────────────┐
 │ CS2 GSI │ 体育数据 API │ 计分器串口/UDP │ 人工录入 │ ASR │
 └───────────────┬─────────────────────────────────────┘
                 │ 原始数据 → 归一化（MatchState patch）
                 ▼
 ┌──────────────── 核心服务 Core Server ───────────────┐
 │  State Store（唯一状态源，rev 版本号）                │
 │  规则引擎（事件 → 自动上/下屏，如「回合结束弹结算」） │
 │  播出控制（图层、TAKE/OUT、Playlist / Rundown）       │
 │  持久化（赛事、队伍、选手、模板配置、操作日志）       │
 └──────┬──────────────────────┬──────────────────────┘
        │ WebSocket 状态推送    │ AMCP / OBS-WS / vMix API
        ▼                      ▼
 ┌─────────────┐      ┌──────────────────────────────┐
 │ 控制台 Control│      │ 图文渲染 Graphics（HTML5）     │
 │ 操作员 UI    │      │ 透明 1920×1080 Browser Source │
 └─────────────┘      └───────────────┬──────────────┘
                                      ▼
                  CasparCG HTML Producer / OBS / vMix / Singular 风格的 Web 输出
                                      ▼
                       Fill + Key（SDI/NDI）或直接叠加 → 切换台 PGM
```

### 核心设计原则

1. **数据与呈现分离**：适配器只产出通用 `MatchState`；模板只订阅状态、不碰数据源。同一个比分条既能吃 CS2 GSI，也能吃足球计分器。
2. **单一状态源**：所有输入（自动数据、操作员指令）汇入服务端 Store，每次变更 `rev + 1` 后广播。图文端随时断线重连都能拿到完整快照，避免「重启浏览器源后图文丢失」。
3. **HTML5 做渲染**：用 Web 技术写模板（CSS/GSAP 动画、Lottie、WebGL），一套模板可以同时跑在 CasparCG、OBS、vMix、Web 预览中，设计师上手快。
4. **播出安全**：模板加载失败、数据异常时不影响其他图层；控制台的所有动作带确认状态（ON AIR 指示）；关键链路主备。

## 3. 技术选型

| 模块 | 选型 | 理由 |
|---|---|---|
| 语言 | TypeScript（前后端统一） | 协议类型共享（`packages/shared`），减少前后端字段不一致的事故 |
| 服务端 | Node.js 22 + `ws`（MVP 用原生 http；后续可迁到 Fastify） | I/O 密集、实时推送场景合适，生态覆盖 GSI/串口/UDP/OSC |
| 控制台 | MVP 原生 HTML → 后续 React + Vite | 复杂表单、Rundown 列表、快捷键、多人协作 |
| 模板 | HTML/CSS/JS ES Module，动画用 GSAP 或 CSS | 每个模板只需实现 `render(el, ctx)`，后续加 `in()/out()` 动画钩子 |
| 播出 | CasparCG（专业 SDI Fill/Key）、OBS / vMix（中小型转播） | 统一使用 Browser Source，播出端只是「浏览器容器」 |
| 存储 | MVP 内存 → SQLite（单机）/ PostgreSQL（多赛事） | 赛事资料、模板预设、操作审计 |
| 部署 | 单机 Docker；现场局域网优先，云端做远程制作 | 现场网络不可靠，核心链路不依赖外网 |

## 4. 数据模型（已在 `packages/shared` 实现）

- `MatchState`：项目无关的通用赛况——主客队、比分、局/节、时钟、`extra`（项目特有数据，如 CS2 经济、炸弹状态、选手列表）。
- `ClockState`：只推送「起点 + 是否运行 + 时间戳」，各端本地计算显示，**不按秒推送**，保证时钟流畅且省带宽。
- `GraphicLayer`：`{ layer, template, visible, data }`，一个图层同时只播一个模板，图层互不影响。
- 消息协议：`graphic.show / update / hide / clearAll`、`match.patch`，服务端统一回推 `state` 快照。

后续演进：快照 → **JSON Patch 增量推送**（高频 CS2 数据量大时），并加入 `event` 消息（击杀、回合结束、进球等离散事件）供模板播放一次性动画。

## 5. 电竞（CS2）专项设计

1. **GSI 接入**：`integrations/cs2/gamestate_integration_livecg.cfg` 放到 OB 机的 `game/csgo/cfg/` 下，游戏会把状态 POST 到 `/gsi/cs2`（token 鉴权）。
   - 必须使用**观察者（OB）客户端**才能拿到 `allplayers_*` 全员数据。
2. **阵营与队伍映射**（M1 已实现，`apps/server/src/adapters/cs2-gsi.ts`）：主客队固定，阵营随半场/加时变化。按以下优先级判断「当前哪队是 CT」：
   1. **选手阵容**：首帧按阵营学习 steamid → 队伍，此后按投票判断。选手不会换队，最可靠；BO3 换图后仍然有效。
   2. **队名**：服务器设置了 `mp_teamname_1/2` 且与控制台队名一致时生效。
   3. **半场标记**：`map.phase` 离开 `intermission` 即换边（比分打平如 6:6 时只能靠它）。
   4. **比分连续性**：漏帧兜底——换边后 CT/T 比分对调。
   5. **手动交换**：控制台一键交换，之后自动跟随。
3. **事件推导**（已实现）：GSI 只给状态，不给事件。适配器对前后两帧做差分：
   - 击杀：`kills` 增量 × 血量 `>0→0` 配对（异队优先），爆头取 `round_killhs` 增量，武器取击杀者当前手持；
   - 回合开始/结束（`round.phase`）、胜利方式（`round_wins`：全歼/爆炸/拆包/超时）、回合 MVP；
   - 炸弹安放/拆除/爆炸、残局（某队首次只剩 1 人，每回合一次）、半场、终局；
   - 换图或回合数倒退时自动清空单图数据（回合历史、ADR），保留阵容。
4. **延迟对齐**（已实现，`delay-queue.ts`）：GSI 数据是「现在」的，而直播常有防作弊延迟（如 90 秒）。所有帧先进延迟队列再解析，事件和状态一起延迟；单队列严格 FIFO，控制台可实时调整延迟。
5. **规则引擎**（已实现，`rules.ts`）：回合结束自动弹出回合结算，到时或下一回合开始自动下屏；规则只发出与操作员相同的指令，可随时手动覆盖。
6. **模拟器与测试**：`pnpm sim:cs2` 生成与 OB 客户端格式一致的整场比赛（含换边、炸弹、经济），无需开游戏即可联调；`pnpm test` 用同一模拟器跑多种子整场回归。
7. **待办 / 已知限制**：
   - GSI 的回合号自增时机以 `round_wins` 推断，需在真实 OB 客户端上核对一次；
   - 击杀配对是启发式的：同一帧多人击杀时只保证「异队配对」，助攻、穿墙、闪光助攻等 GSI 不提供；
   - 加时赛换边依赖 `intermission` 标记，需真机验证；
   - 更多数据（选手历史、BP、赛程积分）来自赛事方 API 或人工录入，留到 M4。

## 6. 传统体育专项设计

1. **计分计时器接入**：多数场馆计分器有串口（RS-232/485）或 UDP 输出协议，做独立适配器即可接入比分与比赛时钟。
2. **官方数据商**：Opta/Sportradar 等提供推送（Push Feed）或轮询 API，适配为 `match.patch` + 事件（进球、换人、红黄牌）。
3. **人工录入兜底**：控制台始终保留手动比分、手动时钟的能力（数据源故障时一键切到手动）。
4. **ASR 实时字幕（可选模块）**：解说音频 → 流式语音识别 → 文本经人工审核队列 → `subtitle` 图层上屏。审核环节必不可少（错字、敏感词）。

## 7. 播出流程与可靠性

M2 已实现以下能力（★ 为尚未实现）：

- **PVW / PGM 双路**（`store.ts`）：`graphic.cue` 预备到 PVW，`graphic.take` 切到 PGM（不指定图层时一次切出全部预备项），`graphic.show` 直接上 PGM（热键、规则引擎使用）。输出页 `?channel=pvw|pgm` 各自独立，可分别接入两路键控或监视器。
- **入/出场动画与图层状态机**（`apps/graphics/index.html`）：每个图层串行地「出场 → 换内容 → 入场」，数据刷新只重绘不重播；`takeId` 区分「数据更新」和「重新上屏」。模板规范见 [TEMPLATES.md](TEMPLATES.md)。
- **播出单（Rundown）**：条目 = 名称 + 模板 + 图层 + 字段数据 + 单键热键。模板通过 `meta.fields` 声明字段，控制台据此生成表单，新增模板无需改控制台。编辑在播条目时只更新数据，不重播入场（实时字幕即依赖这一点）。
- **热键**：空格 TAKE、回车 CUE 并选中下一条、↑↓ 选择、条目热键直接上/下屏、Esc 清 PVW、Shift+Esc 全部下屏；光标在输入框内时不生效；监视器不接收焦点，避免点一下画面热键就失效。
- **外部控制**：`POST /api/command`，body 与 WebSocket 指令完全相同，Stream Deck（Bitfocus Companion 的 HTTP 动作）、脚本、其它系统都可调用。
- **CasparCG**（`casparcg.ts`）：AMCP 客户端对每路输出发送 `PLAY ch-layer [HTML] "<url>"`，之后所有上下屏都在页面内完成，不走 AMCP 往返。配置变化只发送差异（PLAY / CLEAR），断线指数退避重连，CasparCG 重启后自动重新加载。
- **持久化**（`persist.ts`）：配置、播出单、队伍资料写入 `data/runtime/livecg.json`（`LIVECG_DATA_DIR` 可改）；只有这些内容变化时才写盘，先写临时文件再改名防止断电损坏。比分、图层、实时数据不持久化。
- ★ **主备**：两台播出机同时连接同一个 Core Server；Core Server 也可主备（状态持久化 + 重连拉快照）。
- ★ **操作审计**：所有指令记录日志，便于赛后复盘事故。
- ★ **MIDI / X-Keys** 原生支持（目前可经 Companion 转 HTTP）。
